# Day 28 — Local LLM + RAG

Day 28 of my AI challenge: connect the local LLM to the RAG pipeline, then compare it with the
cloud model on quality and speed.

- Use the index from Week 6 (`../doc_index`).
- Retrieval runs locally. It already does: EmbeddingGemma for search and bge-reranker for
  reranking.
- Responses are generated by the local model (Ollama, through the Day 27 `OllamaProvider`).

Hardware: MacBook Air M2, 16 GB RAM, so one local model in memory at a time.

Before writing code, read the Knowledge agent's RAG path: `answer.js`, `contract.js`
(`submit_answer` and `verifySubmission`), `clarify.js`, `router.js` and `chatTurn.js`, the
Day 27 provider code, and `eval:citations`. Reuse them. Don't fork them.

## What to build

### 1. The RAG pipeline with a local generator

- Every model call in a Knowledge RAG chat goes to the chat's selected provider: the
  router (`route`), the answer (`submit_answer`), and the low-relevance clarification
  (`submit_clarification`). The Rewrite stage is out of scope for local. With a local model
  selected, a Knowledge chat with RAG is fully local. Remove the Day 27 "local + RAG: Day 28"
  lock.
- **Forced tool calls become JSON-schema output** for the Ollama provider. Use the same schema
  as the tool's `input_schema`, passed as Ollama's `format`. Then parse and validate the JSON.
  If the JSON is invalid, retry once with the errors.
- **The citation contract is unchanged.** Run the same `verifySubmission` checks (markers,
  chunk_ids, verbatim quotes, 4–60 words) and the same single retry with the error list. The
  retry is sent as a follow-up user message instead of a tool result. After a failed retry,
  drop or downgrade as before. The local model must meet the same bar as Claude, so don't
  loosen any rule.
- **Context window.** Set `num_ctx` explicitly for RAG calls (`LOCAL_RAG_NUM_CTX`), large
  enough for the system prompt, task memory, history, 5 chunks and the reply. If a
  response's `prompt_eval_count` is within 10% of `num_ctx`, log it and flag it on the result
  as `possible_truncation`. Silent truncation is the failure I most want to catch.
- **No silent cloud fallback.** A failed local call is an error or a downgraded answer, never
  a Claude answer.
- In the page, the badge reads like `qwen3.5:9b · rag+rerank` and keeps the metrics on hover.
  Citation chips, the verification badge, sources and "I don't know" work exactly as with
  Claude.

### 2. Compare in the page

Extend **Compare** with a **Claude vs local** option. It sends one question through the same
RAG mode to Claude and to the chat's local model, side by side. Retrieval and rerank run
**once**, and both models answer from the same chunks. Each side shows its answer, citations,
verification badge, and timings: retrieval, rerank, time to first token, generation, total.

### 3. Eval: `npm run eval:local`

- **Questions:** the 10 `citations` questions in `rag+rerank` mode, as in Day 24 (7 to answer,
  3 to decline).
- **Generators:** Claude Haiku 4.5, then each local model in `LOCAL_MODELS`, one after another.
  Unload each local model before loading the next.
- **Same chunks for everyone.** Retrieve and rerank each question once and cache the result in
  `reports/local_rag_retrieval.json`. Every generator answers from identical chunks, so the
  comparison isolates generation. Retrieval and rerank times are reported once, as the shared
  local cost.
- **Judges stay on Claude:** faithfulness and Day 22's fact judge, with `RAG_JUDGE_MODEL`. The
  eval needs the API key for judging only. The report says which calls were cloud and which
  were local.
- **Order and thermals:** record the run order and each request's start time. The Air is
  fanless, so note in the findings whether later questions got slower.
- **Smoke run first:** `npm run eval:local -- --quick` runs 3 questions (one corpus, one
  paraphrased, one decline) on one local model. Run it first.
- Options: `-- --models qwen3.5:9b`, `-- q14`, `-- --report` (re-render only), as in the other
  evals.

Per generator, report:

| quality | speed |
| --- | --- |
| answered with ≥ 1 source / valid citation | time to first token (≈ prompt processing) |
| fabricated quotes on the first attempt | generation tokens/s |
| retries · dropped citations · downgrades | answer latency incl. retry (mean, max) |
| invalid JSON / schema failures (local only) | prompt tokens and output tokens |
| faithfulness (supported / partial / unsupported), uncited claims | model load time (local) |
| correct "I don't know" · false "I don't know" | possible truncations |
| mean fact score | memory in use (from `/api/ps`) |

**Output:** `reports/local_rag_results.json` and `reports/local_rag_report.md`. The report has a
summary with the generators as columns and the table above, then each question with every
generator's answer, citations, verification and timings next to each other. Write
`reports/local_rag_notes.md` with findings from the actual results: where the local models lose
quality and why (quotes, markers, declines, JSON), what the speed is spent on, and whether
local is usable for this task. Add a **Local** tab on `/rag-report`.

### 4. Extend `verify:local`

Add a Knowledge chat with RAG to Day 27's `verify:local`, using the same fetch guard: at least
3 messages, including a follow-up that relies on the task memory. Check that every call went to
the local provider, that no request left localhost, and that the replies have verified
citations.

## Tests

`npm test` stays offline. Use a fake Ollama returning canned JSON and test:
- the JSON-schema path for `route`, `submit_answer` and `submit_clarification`, including
  invalid JSON followed by a valid retry;
- that a contract retry is sent as a user message;
- the truncation flag;
- that a local chat never calls the Anthropic provider;
- that the eval's cached retrieval is reused and all generators get the same chunks.
